# Picoboi 100M architecture and training plan

8 November 2026. Design for a new English conversational model trained from scratch. The deployment target is local inference on ordinary laptops in the browser. The training ceiling is approximately **10 billion processed Picoboi tokens**. Arithmetic, web retrieval and long conversation state have explicit interfaces so the decoder can concentrate on conversation and on explaining results.

The repository has a tied RoPE/SwiGLU decoder with full multi-head attention, an assistant-masked CPU/MPS training path, a JS/CPU browser worker and an optional Wikipedia lookup. The concept parser already binds noun categories to eight conversation references. The local corpus audit records **574,565 English words in 3,429 conversations**, including the two local batches 230–231. English words and the new tokenizer's token count are different units. These are the starting points for the design. ## Decoder and browser budget

| Component | First build |
| --- | --- |
| Transformer | 32 distinct decoder blocks, residual width 512 |
| Attention | Causal grouped-query attention, eight query heads and two key/value heads, head width 64, RoPE |
| Feed-forward | Bias-free SwiGLU, intermediate width 1,504 |
| Norms | Pre-RMSNorm per sublayer and final RMSNorm |
| Vocabulary | 8,192 byte-fallback BPE entries, including control and reference tokens. Shared input/output weights |
| Native context | 2,048 tokens. First train mostly at 512–1,024, then mix 2,048-token sequences before post-training |
| Inference | Web Worker with WebGPU, cached decode, bounded loading and optional WASM fallback after benchmarking |
| Training precision | BF16 where supported with FP32 optimizer state. First export FP16 and INT8 references, then calibrate and measure INT4 |

Parameter count with no biases or extra heads:

```
tied embedding   8,192 × 512                         =  4,194,304
attention        32 × (2 × 512² + 2 × 512 × 128)     = 20,971,520
SwiGLU           32 × 3 × 512 × 1,504                = 73,924,608
RMSNorm          (2 × 32 + 1) × 512                  =     33,280
total                                                = 99,123,712
```

This requires adding GQA to the repo's model, parameter checker and export path. Train and export against the same attention layout. Benchmark the 32-layer design against a wider, shallower near-100M configuration at matched data and compute, since per-layer dispatch cost matters in a browser. Keep the full-attention GQA model as the reference. The closest research precedent is MobileLLM's deep, narrow models with tied embeddings and GQA. The 2026 ICLR architecture study covers 80M–3B models and studies the effect of width, attention and MLP allocation at 8B–100B training tokens. Its results motivate an experiment at this size. [MobileLLM](https://arxiv.org/abs/2402.14905) · [GQA](https://arxiv.org/abs/2305.13245) · [ICLR 2026 architecture scaling study](https://proceedings.iclr.cc/paper_files/paper/2026/hash/dd2eb5250696753ea37141bbd89bb569-Abstract-Conference.html)

Uniform weight payloads are **198.25 MB FP16, 99.12 MB INT8 and 49.56 MB INT4** before metadata and scales. A more concrete INT4 layout with 4-bit linear matrices, FP16 scales per 64 weights, INT8 tied embeddings and FP16 norms is about **54.7 MB** before other quantization metadata, alignment and tokenizer files. FP16 KV cache is **32 MiB** at 2,048 tokens and batch size one. Keep packed weights resident if the selected kernels support it, and measure actual peak memory including dequantization, load copies and workspace. Check exported logits and generated sequences against PyTorch, including GQA cache indexing and tied weights. Start with a small ONNX Runtime Web export and profile operator coverage and real packed decode on Chrome and Safari. A custom WGSL path becomes worthwhile if the runtime inflates memory or misses latency targets. [ONNX Runtime Web](https://onnxruntime.ai/docs/tutorials/web/)

### DeepSeek ideas and experiment order

| Research finding | Picoboi decision |
| --- | --- |
| V3 combines MLA, MoE and a multi-token prediction objective. [V3 report](https://arxiv.org/abs/2412.19437) | Start with GQA and a dense model sized by **total** parameters and download. Pilot a single auxiliary next-next-token prediction step with a shared vocabulary head at matched training FLOPs. Drop that module from the serving graph and account for its training cost separately. Test MLA later if the measured KV cache becomes the main constraint. |
| V3.2 uses an indexer for sparse long-context attention. V4 interleaves compressed sparse and heavily compressed attention and introduces mHC and Muon in its recipe. [V3.2](https://arxiv.org/abs/2512.02556) · [V4](https://arxiv.org/abs/2606.19348) | Put recent chat and retrieved evidence under a tight context budget. Test a 512-token local window in 24 layers with eight evenly spaced global layers, training with those masks. Its theoretical FP16 KV cache is **14 MiB** with bounded local buffers. Test topic changes and delayed references before adopting it. Use AdamW for the reference and consider Muon as an isolated training experiment if pilots justify it. |
| V4.1-Flash combines cross-layer cache reuse, FP4 caching, bounded sliding-window replay and different prefill/decode compute paths in a 552B backbone. [V4.1-Flash, September 2026](https://arxiv.org/abs/2609.19969) | Reuse stable prompt prefixes and benchmark INT8 KV after weight quantization. Cross-layer cache sharing, low-bit KV and asymmetric prefill require separate accuracy and kernel experiments. The reported savings are for a very different model and workload. |
| MobileLLM-Flash measures architecture choices against device latency. MobileMoE demonstrates sparse on-device execution with substantially larger total models and dedicated kernels. [MobileLLM-Flash, ACL 2026](https://aclanthology.org/2026.acl-industry.51/) · [MobileMoE, 2026](https://arxiv.org/abs/2605.27358) | Choose a browser configuration using measured prefill and decode. Keep layer sharing and MoE as research comparisons if a total-size-matched variant earns its runtime complexity. |
| BitNet trains ternary linear weights and relies on packed kernels. [BitNet b1.58](https://arxiv.org/abs/2402.17764) · [2B4T report](https://arxiv.org/abs/2504.12285) | Preserve the original ternary idea as a separate small matched pilot. Compare quality and wall time against BF16 training plus INT4 export. Ternary packing at two bits costs about 23.7 MB for this model's linear matrices alone. Count scales, embeddings and norms separately and require an actual packed browser kernel before adopting it. |

## Vocabulary and entity parser

Treat the original 968-word list as a **simple English style seed**. Train an 8,192-entry tokenizer on the proposed mixture, with byte fallback so ordinary unfamiliar words, names and source quotes can still pass through. Measure 4,096 vs 8,192 entries at comparable parameter and compute budgets. Compare tokens per UTF-8 byte, latency and response quality, since a tiny vocabulary can expand sequence lengths. Train the tokenizer on the train partition only.

Start entity normalization with cities. For example, “from Delhi to Mumbai” becomes `from <city> <ref_1> to <city> <ref_2>`. The browser parser owns a table of surface spelling, type, canonical identity where resolved and source span. The model sees reusable types and references. Reserve 32 generic reference IDs inside the vocabulary budget for the first experiment. Scope them to a conversation, preserve IDs through compaction and resolve repeated mentions to the same ID. Match multiword names and boundaries, preserve ambiguity such as a person named Paris, and keep raw text on misses, collisions and overflow. Use the original span when constructing queries; resolve model references before sending tool arguments. Render only valid references, with type checking and the original spelling. Use the same transformation in Python data preparation and browser inference. Normalize both sides of training dialogues with a shared table and supervise emitted references only if the runtime would know them by that point. Preserve a raw-text view and evaluate novel names, two-city swaps, correction across turns and citations. Extend categories after the city experiment earns its cost.

Entity compression preserves identity and can reduce name memorization. When a question depends on a property hidden by compression, attach the relevant dictionary record or retrieved evidence. Preserve negation, units, numbers, relations and exact quoted text. A style preference for simple words applies to normal chat; source titles, quantities and user quotations have their own fidelity requirements.

## Runtime behavior and tools

Keep the router and tool execution in the client, separate from decoder weights. The host validates model proposals against a small tool grammar and allowlisted schemas. Use special role and control tokens for tool calls and observations. At decode time allow only valid token transitions for the chosen tool; parse and validate the result again. Initially permit two calls per turn with separate time and evidence budgets. The policy handles ordinary chat locally, routes explicit arithmetic through the calculator and routes requests for sources, current facts and lookup through search when enabled. For ambiguous intents the decoder can propose a tool or ask a clarifying question. A model's verbal confidence alone is a weak lookup signal. Measure routing errors, including unnecessary browsing, against labelled queries.

### Calculator

1. Recognize unambiguous arithmetic directly from user text. For a word problem let the decoder propose an expression and an optional unit, with operands traceable to the user or a confirmed prior result.
2. Parse an allowlisted grammar into an expression tree with explicit precedence and unary operators. Use bounded exact integer/rational operations and a documented decimal rounding policy for display. Support percentages explicitly, including “percent of” versus “increase by percent”. Reject invalid syntax, division by zero, excessive exponents and unsupported units. Ask for clarification when inputs are missing or the expression is ambiguous.
3. Inject a typed tool observation containing the canonical expression, value and unit. Render the authoritative value from the tool via a validated result slot or a deterministic sentence. Let the model explain the result in chat; check any echoed value and fall back to the tool rendering on disagreement. Train on successful calls, malformed arguments, corrections, missing inputs, follow-ups and ordinary numerical chatter that needs no call. Generate expression/result pairs with the actual engine and hold out expression families.

### Search, scrape and summarize

Use the existing optional Wikipedia lookup as the first connector. Add a search-provider adapter and a bounded URL fetcher. CORS-enabled sources can be fetched in the browser. General public-web coverage requires an optional fetch service, or a browser extension with user-granted host access. With a fetch service, inference and personal memory stay in the browser; the service receives a minimal search query or requested URL and returns cleaned public text. Keep credentials server-side. The site can also accept a user-pasted page or local file as evidence. [Browser CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS) · [Mozilla Readability](https://github.com/mozilla/readability)

- Fetch a bounded number of public HTTPS results, with request, byte and redirect limits. Honor source terms and robots rules; respect paywalls and authentication. Revalidate each redirect and block private, local and link-local addresses at DNS resolution and connection time. Use inert HTML parsing and render escaped text. Add PDF extraction and a restricted JS rendering fallback only after the basic fetcher is stable. [Robots Exclusion Protocol](https://www.rfc-editor.org/rfc/rfc9309.html)
- Extract title, URL, date when available, headings and paragraph text. Deduplicate by URL and content. Split by headings into 120–240-token passages and rank on the client using lexical matching, with original names, dates and units retained. Start with up to three sources and a 600-token evidence cap. Prefer primary sources and keep stable evidence IDs plus fetch timestamps. Rank around the current question and active conversation entities rather than summarizing a whole page indiscriminately.
- Pass evidence as tool data with validated source IDs. Page text has no authority to issue instructions, call tools or modify state. The decoder generates a short answer grounded in the returned passages. Resolve citations through the host. Where a result is missing, weak or conflicting, ask for a URL, show the disagreement or return relevant quoted passages. A citation ID alone does not establish support, so evaluate claim-to-passage grounding. Keep a deterministic snippet fallback for low-quality synthesis.
- The web path is opt-in and visibly online. Send the query, not the transcript. Cancel fetch and generation together on New Chat, and reject stale results using turn IDs.

### Automatic context compaction

Keep the transcript, bindings and evidence records in a local state store. With 2,048 tokens, start with a budget of 160 for instructions/tool framing, 240 for structured memory, 720 for recent dialogue and current request, 600 for evidence and 328 for output. Reallocate unused evidence space to chat. Count real tokenizer output. Compact before a turn overflows rather than slicing a message or a tool call/result pair. Preserve the current request and essential evidence first; if a single pasted document is too long, retrieve excerpts or ask the user to narrow it.

Keep authoritative facts in typed records with source turn IDs: preferences, active task, entity bindings, quantities, unresolved questions and tool results. Retain recent turns verbatim, keep older text available for exact recall, and retrieve relevant older turns when needed. An optional short summary can explain how older turns fit together. It cannot overwrite explicit user facts; newer corrections supersede older values with provenance. Test resuming after topic changes and contradictory updates. Reuse KV for unchanged prefixes; rebuild affected cache entries after compaction. Use prompt compression research as an experiment for retrieved passages, with citation spans, units and negation protected. [LongLLMLingua](https://arxiv.org/abs/2310.06839)

## Dataset sources and 10B training schedule

Use measured, **post-tokenization processed tokens**, tracking unique tokens, processed tokens and loss-bearing tokens separately. These allocations are targets conditional on a deduplicated, permitted source inventory. A large chat dataset's row count or a GPT-2 token estimate does not establish Picoboi's available tokens.

| Stage | Processed tokens | Sources and purpose |
| --- | ---: | --- |
| English base | 4.0B | Approximately 3.7B filtered accessible English prose from [FineWeb-Edu](https://huggingface.co/datasets/HuggingFaceFW/fineweb-edu), starting with its streaming 10BT sample and expanding the sample only if needed, plus up to 0.3B [TinyStories](https://huggingface.co/datasets/roneneldan/TinyStories) tokens. Cap repeated story exposures; backfill from the prose pool. Train full next-token targets. |
| Conversation continuation | 5.8B | Target 5.5B dialog-shaped tokens plus 0.3B prose replay. Source filtered everyday English exchanges from [SmolTalk2](https://huggingface.co/datasets/HuggingFaceTB/smoltalk2), [Smol-SmolTalk](https://huggingface.co/datasets/HuggingFaceTB/smol-smoltalk), [UltraChat 200k](https://huggingface.co/datasets/HuggingFaceH4/ultrachat_200k) and relevant components of [Tülu 3 SFT mixture](https://huggingface.co/datasets/allenai/tulu-3-sft-mixture). Cap verbose tutorials and technical tasks. If the useful dialogue supply falls short, pilot conversion of additional permitted prose into concise, evidence-linked conversations with a teacher and review their quality before scaling. Train both dialogue roles here, with explicit role markers. |
| Assistant/tool post-training | 0.2B | Budget about 100M everyday chat, 35M calculator and routing, 40M grounded lookup, and 25M memory, entity and recovery traces. Use assistant/tool-call targets only. Sample the original local corpus deliberately for style and follow-up behavior, with a capped repeat count and a held-out split. Adapt the relevant parts of [ToolACE](https://huggingface.co/datasets/Team-ACE/ToolACE) into the real tool schema. Build evidence and unanswerable examples from [SQuAD v2](https://huggingface.co/datasets/rajpurkar/squad_v2) and multi-passage examples from [HotpotQA](https://huggingface.co/datasets/hotpotqa/hotpot_qa). Generate deterministic calculator results, replay captured web fixtures and use real compaction outputs for memory examples. |

The desired mix has **5.7B dialogue-shaped processed tokens**, including tool conversations, versus 4.3B prose/story tokens. Verify this before booking the full run. Stream and profile a representative sample of each dataset first. Pin dataset revision, config, split, language, source/license metadata and content hash. Audit upstream terms per component and remove PII, malformed turns, very verbose answers and duplicate source families. Keep document, prompt family, entity and template holdouts across derived data; split before normalizing, paraphrasing or deriving tool traces. Track exact and approximate dedup across datasets, especially reused chat mixtures. Set a provisional cap of three exposures per imported dialogue during continuation; 5.5B processed dialogue tokens then needs at least roughly **1.83B usable unique dialogue tokens**, with more required for uneven exposure counts. If the inventory or teacher pilot misses the threshold, train the measured smaller mixture and report the remaining budget. The 10B target gives no reason to recycle a small pool indefinitely. Review legal and release suitability before distributing data or weights. [HF streaming](https://huggingface.co/docs/datasets/stream) · [SmolLM2 data recipe](https://arxiv.org/abs/2502.02737) · [TinyStories paper](https://arxiv.org/abs/2305.07759) · [Toolformer](https://arxiv.org/abs/2302.04761)

## Training, cost and launch gates

- Implement a CUDA BF16 path, packed batches with document boundaries respected, and a token-based scheduler. Reuse the current resume and assistant-mask conventions for post-training. Tool results, user text and padding are context during SFT, with model-produced calls and answers as supervised targets. Persist optimizer, RNG, tokenizer/data revision and sampler position in checkpoints; verify interrupted resume on a small run. Start AdamW with gradient clipping, warmup and decay; sweep learning rate and token batch on a small pilot before locking the full schedule.
- Run a 10–50M-token end-to-end smoke run, then a matched 100–300M-token pilot for tokenizer, architecture and data choices. Continue the winning recipe with validation at approximately 1B, 3B, 6B and 10B tokens. Track held-out loss within each tokenizer, and compare different tokenizers with normalized loss on common text plus task scores. Ten billion tokens is about 101 tokens per model parameter. This is a design budget for an inference-constrained model, with checkpoints to test marginal gains. [Chinchilla](https://arxiv.org/abs/2203.15556) · [Inference-aware architecture scaling](https://proceedings.iclr.cc/paper_files/paper/2026/hash/dd2eb5250696753ea37141bbd89bb569-Abstract-Conference.html)
- Rough training scale is `6 × 99.1M × 10B ≈ 5.95 × 10^18 FLOPs` before attention-length effects, auxiliary training and overhead. Compare low-cost single-GPU rentals on measured useful tokens/sec and total storage/checkpoint cost; start with a short benchmark on a rentable 24 GB CUDA GPU if it fits the actual token batch. At sustained 10k / 25k / 50k processed tokens/sec, a 10B run takes about 278 / 111 / 56 GPU-hours respectively. Multiply by the live hourly quote when renting and add preemption, eval and I/O time. Use spot capacity only after resume works. These rates are budgeting scenarios rather than hardware forecasts.
- Freeze a held-out test suite before training. Score natural chat, short rewrite instructions, references with unseen names, long-delay corrections, exact arithmetic routing/arguments/results, and evidence-supported answers and abstention. Include hard negatives where calling a tool is unnecessary, inaccessible URLs, conflicting evidence, and instructions embedded in scraped pages. Use frozen web fixtures for regression and a small live set for coverage and latency. Assess answer style, not just grammar, against the local corpus and comparable small-model baselines. [MobileLLM-125M](https://huggingface.co/facebook/MobileLLM-125M)
- Provisional release gates: zero wrong numbers on the deterministic calculator suite, at least 95% correct calls on unambiguous supported arithmetic, at least 95% correct rendered entity references on held-out names, and at least 90% supported claims on the fixed web fixture set. Track abstention and answer coverage alongside grounding. Compare compaction against full retained context for cases that fit, with exact user corrections and numeric facts as required cases. Record sample counts and failure examples. Measure cold start, time to first token, decode speed and peak memory on representative laptop browsers. Initial warm target is at least 10 tokens/sec on the reference WebGPU laptop with a 512-token prompt. Quantization earns release only if chat and tool evaluations stay within the predefined regression budget, initially two percentage points on each aggregate suite.
- Build in order: **data inventory and tokenizer pilot → 100M CUDA/GQA reference and browser export → calculator plus tool traces → web evidence and compaction → matched research experiments → scale the winning recipe**. Keep research branches and budget estimates separate from measured browser results.
